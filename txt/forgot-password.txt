BASE URL
--------
Local development : http://hubli.test/api
Production        : https://YOUR-LIVE-DOMAIN/api
(All endpoints below are relative to the base URL.)

All requests must send these headers:
    Accept: application/json
    Content-Type: application/json

No authentication token is required for these two endpoints
(the user is logged out — that is the whole point).


================================================================================
 HOW THE FLOW WORKS (READ THIS FIRST)
================================================================================

 STEP 1  User taps "Forgot Password?" in the app and enters their email.
         App calls:  POST /api/forgot-password

 STEP 2  The server emails the user a reset link + a reset TOKEN.
         The email contains:
           - A "Reset Password" button that opens the WEBSITE reset page
             (http://hubli.test/reset-password/{token}?email=...)
           - The raw TOKEN and EMAIL printed as text, so the user can
             copy them into the app if the app has its own reset screen.

 STEP 3  The user resets the password in ONE of two ways:

         OPTION A (easiest - no extra app work):
           User clicks the email button, resets the password on the
           website, then returns to the app and logs in with the new
           password using the normal POST /api/login.

         OPTION B (in-app reset screen):
           The app shows a screen with fields:
              email, token, new password, confirm password
           The user copies the token from the email into the app.
           App calls:  POST /api/reset-password

 STEP 4  After a successful reset, the user logs in again with
         POST /api/login and the NEW password. All previously issued
         API tokens remain valid until the next login (login deletes
         old tokens and issues a fresh one).

 NOTE ON DEEP LINKS (optional, advanced):
   If you want the email button to open the APP instead of the website,
   ask the backend admin to set FRONTEND_URL in the server .env file
   to your deep-link/universal-link base (e.g. https://app.hubli.com).
   The email link then becomes:
       {FRONTEND_URL}/reset-password?token=XXX&email=YYY
   Your app must catch that URL, extract "token" and "email", and open
   the in-app reset screen (then continue with Option B).
   If FRONTEND_URL is NOT set, the email links to the website page and
   everything still works (Option A).


================================================================================
 ENDPOINT 1: REQUEST A PASSWORD RESET LINK
================================================================================

 METHOD : POST
 URL    : /api/forgot-password
 AUTH   : none

 REQUEST BODY (JSON)
 -------------------
 {
     "email": "user@example.com"
 }

 FIELD RULES
 -----------
 email : required, must be a valid email format

 SUCCESS RESPONSE - HTTP 200
 ---------------------------
 {
     "message": "We have emailed your password reset link!"
 }

 ERROR RESPONSES
 ---------------
 HTTP 400  (email not found in users table)
 {
     "message": "We can't find a user with that email address."
 }

 HTTP 400  (throttled - a link was already sent less than 60 seconds ago)
 {
     "message": "Please wait before retrying."
 }

 HTTP 422  (validation failed - missing/invalid email)
 {
     "message": "The email field is required.",
     "errors": {
         "email": ["The email field is required."]
     }
 }

 IMPORTANT
 ---------
 - The reset TOKEN expires after 60 minutes.
 - Only ONE token is valid per user at a time. Requesting a new link
   invalidates the previous token.
 - Throttle: the user must wait 60 seconds between requests.


================================================================================
 ENDPOINT 2: RESET THE PASSWORD WITH THE TOKEN
================================================================================

 METHOD : POST
 URL    : /api/reset-password
 AUTH   : none

 REQUEST BODY (JSON)
 -------------------
 {
     "token": "6c43215e02f2830d4f223ef37afb7361c9e5b5a1...",
     "email": "user@example.com",
     "password": "newSecret123",
     "password_confirmation": "newSecret123"
 }

 FIELD RULES
 -----------
 token                 : required (the token from the reset email)
 email                 : required, valid email, must match the account
 password              : required, minimum 8 characters
 password_confirmation : required, must exactly match "password"

 SUCCESS RESPONSE - HTTP 200
 ---------------------------
 {
     "message": "Your password has been reset!"
 }

 ERROR RESPONSES
 ---------------
 HTTP 400  (token invalid, already used, or expired)
 {
     "message": "This password reset token is invalid."
 }

 HTTP 400  (email does not belong to any user)
 {
     "message": "We can't find a user with that email address."
 }

 HTTP 422  (validation failed)
 {
     "message": "The password must be at least 8 characters.",
     "errors": {
         "password": ["The password must be at least 8 characters."]
     }
 }

 AFTER SUCCESS
 -------------
 Send the user to the login screen and call the normal login:

     POST /api/login
     { "email": "user@example.com", "password": "newSecret123" }

 which returns the fresh Sanctum bearer token + user object as usual.

 QUICK TEST WITH CURL
================================================================================

 1) Request the link:
    curl -X POST http://hubli.test/api/forgot-password \
         -H "Accept: application/json" \
         -H "Content-Type: application/json" \
         -d "{\"email\":\"user@example.com\"}"

 2) Open the email, copy the token, then:
    curl -X POST http://hubli.test/api/reset-password \
         -H "Accept: application/json" \
         -H "Content-Type: application/json" \
         -d "{\"token\":\"PASTE_TOKEN_HERE\",\"email\":\"user@example.com\",\"password\":\"newSecret123\",\"password_confirmation\":\"newSecret123\"}"


================================================================================
 SUGGESTED APP UI FLOW (FLUTTER PSEUDO-FLOW)
================================================================================

 LoginScreen
   └── "Forgot Password?" text button
         └── ForgotPasswordScreen
               - one email TextField
               - "Send Reset Link" button  ->  POST /api/forgot-password
               - on 200: show "Check your email" message and a button
                 "I have the code" -> ResetPasswordScreen
               - on 400/422: show response "message" to the user
         └── ResetPasswordScreen
               - fields: email (prefilled), token, new password,
                 confirm password
               - "Reset Password" button  ->  POST /api/reset-password
               - on 200: navigate to LoginScreen with success toast
               - on 400: token wrong/expired -> tell user to request
                 a new link
               - on 422: show field errors from "errors" object


================================================================================
 WEBSITE PAGES (FOR REFERENCE - ALREADY LIVE)
================================================================================

 GET  /forgot-password           -> web form to request the reset email
 POST /forgot-password           -> sends the email (web form submit)
 GET  /reset-password/{token}    -> web form opened from the email link
 POST /reset-password            -> performs the reset (web form submit)
 GET  /reset-password?token=X&email=Y
                                 -> also accepted (redirects to the form
                                    above), so deep-link style URLs work
                                    in a browser too

 The "Forgot password?" link on http://hubli.test/login points to
 /forgot-password. The web flow and the API flow share the same token
 system (password_resets table), so a token emailed once can be used
 EITHER on the website OR through the API - whichever the user chooses.


================================================================================
 SERVER-SIDE NOTES (FOR THE BACKEND / DEVOPS PERSON)
================================================================================

 - Emails are sent through the SMTP settings (MAIL_*) in .env.
 - Token lifetime + throttle: config/auth.php -> passwords.users
   (expire = 60 minutes, throttle = 60 seconds).
 - The email template is built in:
     app/Notifications/ApiResetPasswordNotification.php
 - API controller:  app/Http/Controllers/Api/AuthController.php
   (forgotPassword / resetPassword methods)
 - Web controller:  app/Http/Controllers/AuthController.php
   (showForgotPasswordForm / sendResetLink /
    showResetPasswordForm / resetPassword methods)
 - DOMAIN IS FULLY DYNAMIC: the email link is generated from the
   domain the request came in on. Deploy the same code on any domain
   (hubli.test, your live domain, anything) and the reset links just
   follow it - no config change needed.
 - Set APP_URL in .env to the real domain in production anyway, so
   links generated from console/queued jobs are also correct.
 - Do NOT set FRONTEND_URL to this website's own domain - leave it
   unset. Only set it if a SEPARATE frontend app (SPA / mobile deep
   link) should receive the email link instead (see "deep links"
   note above). It is read via config('app.frontend_url'), so run
   "php artisan config:cache" after changing it in production.
